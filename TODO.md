# Power Toys — review findings

Severity: **high** the user sees something wrong or missing, or the item blocks
other work · **medium** it makes changes slow or risky, or costs the user
comfort · **low** polish, tidying, convenience.

Effort: **XS** minutes · **S** under an hour · **M** an hour or a few · **L** a day or more.

Review scope: runtime source, configuration, install/uninstall paths, policy,
udev rules, styles, icons and documentation. Cache, build output, tests and
test-only tooling were excluded as requested.

Review categories: functional correctness; reliability, lifecycle and
concurrency; security and permissions; performance and resource use; UX and
accessibility; internationalization; compatibility and maintainability;
architecture and SOLID; coupling; wiring and integration; state management;
installation and operations; testing and quality assurance; documentation and
assets. Each item names its primary category even where the impact crosses
categories.

| PT-379 | Security and permissions | blocked | S | medium | `powertoys-helper:262-290` silently rewrites `charge_control_start_threshold` to `value - 5` (floored at 0) whenever the existing start threshold is at or above the requested end threshold, and restores it only if the transaction fails - so on success a node TLP and vendor utilities commonly own is permanently changed, with nothing in the README, the polkit `<message>` or the applet's change notification saying so. | PT-423 | Testing and quality assurance | rejected/won't fix | M | medium | `make coverage` measures 6798 lines - 67.7% of the applet - and lists the other 3246 as unmeasured. Now that PT-420 evaluates those files, measuring them looked like the obvious next step, and it is not one. Loading a module runs its body and nothing else: every method of `PowerToysApplet` and of the widget classes would be measured at zero, which is some six hundred functions against a gate that is per function and set at 80%. Reaching them means constructing the applet, and construction is where the absence of a session stops being survivable - a plain `St.Label` builds outside a stage, but `PopupMenu.PopupBaseMenuItem` takes the process down with it. So the figure would either fail permanently or need a second threshold nobody could ever raise, and the honest report is the one the run already prints: what it measured, and what it did not reach. |

| PT-444 | Functional correctness | blocked | S | low | A monitor is recognised across a re-detection by `display.bus`, and where ddcutil publishes no I2C bus `lib/ddc.js` `_adopt` falls back to `"display:" + number` - a key the same file's own comment calls "a position in ddcutil's own list" that "shuffles up when something earlier is unplugged". The EDID comparison behind it does not save that case: `DdcParse.sameDisplay` answers true when neither side has a manufacturer, model or serial, because it is written to treat a missing field as unknown rather than different - which is right for a marginal reply that drops one field and is an answer about nothing when all three are absent. So on a machine with no bus and no readable EDID, unplugging the first of two monitors hands the second one the first's slider: its name, its last brightness and its raw scale. Blocked: the obvious fix - refuse to adopt when there is nothing to compare - destroys and rebuilds every monitor on every detection on exactly those machines, throwing away brightness values and any drag in progress, and which of the two is the better wrong answer for hardware neither of us can put on a desk is the owner's call. Not seen on a machine; found by reading. |
| PT-448 | Installation and operations | open | XS | low | `tools/build-package.py` states a mode for every archive entry - 0644, and 0755 for the helper - on the ground that a mode read off the build machine is not a property of the release, and `payload()` then skips directories, so the archive carries no directory entries at all. `lib/`, `ui/`, `icons/` and `po/` are created by whatever unpacks it, at that machine's umask: 0775 where it is 002. install.sh states directory modes since the modes were stated there, and `tests/cases/install.js` checks them; the archive path is the one that still does not. |
| PT-443 | UX and accessibility | blocked | S | low | The first-run notification (`applet.js` `_introduce`) tells every user that "the wheel over the icon changes screen brightness, a middle click toggles the keyboard backlight". Both are the defaults, and on a desktop with no kernel backlight and no keyboard backlight neither does anything: the one notification somebody is certain to read names two gestures that are inert on their machine, and the row exists because that notification is explicitly the applet's one chance to teach them. Naming only what the machine can do means asking `_input.capabilities()`, and the greeting is delivered from `_begin` while the settings-daemon backlight probe and any DDC detection are still in flight - so a capability-checked greeting on a laptop would say the wheel does nothing, which is worse than the current over-claim. Blocked: either the greeting waits for the probes to settle (and a first-run notification that arrives seconds after the applet may be missed entirely) or it keeps naming the defaults and is wrong on desktops - which of those the greeting is for is the owner's call. |
